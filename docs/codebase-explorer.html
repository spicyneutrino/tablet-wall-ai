Historical snapshot of commit 0899e04, dated 7 October 2026. For current code and controls, use the current field guide and operator runbook.

Many tablets. One picture. Every seam computed on purpose.

A FastAPI server keeps one shared “wall” in wall units. Each tablet browser draws only its own slice. An operator page arranges the tablets and picks what they show. This guide teaches how that works, why it is built this way, and how to change it safely.

Orientation · 01

What the project is

tablet-wall-ai turns a set of tablets into one coordinated display wall. It is a small client/server web app. The “ai” in the name is historical; the README states that no AI capability exists or is planned.

Tablet code

Opens /client/. Keeps a device UUID in localStorage. Registers over HTTP, holds a WebSocket, sends a heartbeat every 5 s, and paints its slice on a canvas.

frontend/client/client.js · 1,824 lines

Operator code

Opens /controller/. Sees the live roster. Edits the wall size and each placement with number fields. Picks colour, calibration or a curated image. Saves and recalls named layouts and scenes.

frontend/controller/controller.js · 4,088 lines

Server code

One FastAPI process. It validates commands, writes the wall to SQLite, keeps the roster in memory, and pushes frames over WebSockets. It also serves both pages and the image bytes.

main.py 1,448 · tabletwall/ 1,159 lines

What the wall can show today

  • Colour: each tablet shows the colour the operator assigned to it (the original protocol v1 behaviour).
  • Calibration: each placed tablet draws its slice of one grid pattern with wall-wide diagonals. Use it to check geometry and seams.
  • Image: one curated JPEG or PNG, scaled with centred cover across the whole wall. Each tablet clips its slice.

What does not exist README

  • No authentication or authorization inside the app.
  • No upload endpoint, no video, no clock synchronisation.
  • No Dockerfile, Compose file, or CI workflow in the repository.
  • No per-tablet “I painted it” acknowledgement. The server knows what it sent, not what a screen shows.

Orientation · 02

The mental model in four sentences

1. The server holds one wall: a layout (where screens are), a scene (what to show), and two ordering tokens (revision, generation).

2. Operators change the wall with HTTP commands. The server saves the change to SQLite first, then changes memory, then pushes it.

3. Every tablet receives a complete wall frame over its WebSocket. It contains only that tablet’s own placement.

4. Each tablet computes the same wall-space picture and draws only the part behind its own glass. That is why the seams line up.

Synchronous vs asynchronous

  • HTTP command → response is request/response. The operator waits for the status code.
  • WebSocket pushes are fire-and-forget. HTTP does not wait for tablets to render.
  • The only background task is the heartbeat sweeper, an asyncio task inside the same process.
  • Asset scans run in worker threads (asyncio.to_thread, or plain def routes). SQLite calls run on the event loop.

Startup to normal operation

  1. uvicorn imports main.py; static dirs mount by relative path.
  2. lifespan() loads the wall row, mints a new generation, saves it.
  3. assets.refresh() scans images; an unreadable directory stops startup.
  4. The sweeper task starts. Requests are served.
  5. The roster is empty until tablets re-register, which they do on their own.

Architecture · 05

Module dependencies

Arrows point from importer to imported module. The graph has no cycles. Select a module to highlight what it needs and what needs it.

Deliberate coupling: shared object identity

main.py imports devices, wall, device_sockets, … by name and re-exports them. Tests reset them through main. So these objects must be mutated in place (wall.clear(); wall.update(…)), never reassigned. Reassigning wall = {...} in one module silently splits the state in two.

Browser ↔ server coupling

The JavaScript files import nothing from Python. Their only contract is the wire format in PROTOCOL.md. A change to a frame shape must update the server projector (state._wall_frame, _wall_state), both pages, PROTOCOL.md and the tests together.

Boundary notes deep dive

  • main.py mixes four layers: Pydantic models, route handlers, orchestration (_commit_wall) and some domain rules (auto-arrange geometry, saved-snapshot validation). It is a “fat entry point”, not a strict layered design.
  • state.py imports fastapi.WebSocket only for type hints of the socket registries. It does no I/O.
  • hub.py is imported only by main.py. It never imports persist, so delivery cannot write to disk.
  • _valid_saved_layout() re-implements the placement rules that PlacementCommand enforces. A placement schema change must update both.
  • The simulator imports main and drives the real app. It is the only non-test code that depends on the server.

Runtime · 08

The commit boundary: save, then apply, then tell

Every route that changes the wall calls _commit_wall(change) in main.py. It is the most important invariant in the backend. Run it below, with and without a failing disk.

def _commit_wall(change):
    proposed = deepcopy(wall)        # 1 detached copy
    change(proposed)                 # 2 mutate the copy
    proposed["revision"] += 1
    save_state(proposed)             # 3 SQLite commit (may raise)

    # Reached only when the write committed.
    change(wall)                     # 4 same change, live dict, in place
    wall["revision"] += 1

# caller (every wall route):
_commit_wall(apply)
await _broadcast_wall()              # 5 tell sockets, only now

Why this order

If save_state raises, nothing in memory has changed and nothing was broadcast. Memory, disk, and what every client was told still agree. The route fails loudly with a 5xx. PROTOCOL.md

Two rules the callback must obey

  • change runs twice. It must be deterministic and have no side effects of its own.
  • No await may appear between steps 1 and 4. Other coroutines must never see a half-applied wall.

Revision and generation: who wins when frames arrive late

A tablet must ignore old frames, or a reconnect replay could roll the wall back. But a server restored from backup may legitimately hold a lower revision. The generation token solves both. Try the events below.

Client rule (client.js applyWallFrame, same rule in controller.js): reject a frame only if its generation equals the held generation and its revision ≤ the held revision. Otherwise accept it and reset the held pair.

Runtime · 11

Concurrency: one event loop, a few threads, many sockets

Shared state is plain dicts with no locks. Safety comes from one rule: never await while a mutation is half done. Every await is a point where another request, socket, or the sweeper can run.

ConcernWhat the code doesResidual risk
Half-applied state_commit_wall, registration and device delete mutate before their first await.A future edit that adds an await inside apply breaks this silently. inferred
Broadcast while sockets changeIterate over list(...) copies; each send in its own try; failed controller sockets are discarded and closed.Sends are sequential with no timeout. One slow socket delays later recipients.
Two sockets for one deviceThe newest socket takes the slot before any await; the old one is closed with 4409 and its task skips the offline broadcast.Two browser tabs on one origin share a UUID and keep replacing each other.
Heartbeat from a replaced socket_device_loop updates last_seen only if this socket still owns the slot.None found.
Sweeper vs reconnect_sweep_once re-checks slot identity and age just before closing.None found. Covered by the simulator 22_sweeper scenario.
Competing operatorsEach HTTP write applies in completion order.Last write wins. No revision precondition (no optimistic concurrency) on PUT routes.
Blocking I/OAsset scans run in threads. SQLite writes run on the loop.A slow disk stalls heartbeats and broadcasts while save_state runs. inferred
Controller livenessController sockets have no heartbeat.A vanished controller is removed only when a later send fails.
Inventory swapassets.refresh() replaces _inventory wholesale, so a thread reader sees old or new, never partial.Many parallel tablet fetches each rescan the whole directory (CPU, I/O).

Cancellation detail. hub._broadcast_offline runs its sends inside anyio.CancelScope(shield=True), so a socket task that is being cancelled still tells controllers that the device went offline.

Consequence you will see in practice. After a restart, placements exist before their devices re-register. The controller shows them as vacant reservations. POST /wall/auto refuses (409) to cover a reservation instead of deleting it. Releasing one is an explicit DELETE /devices/{id}/placement.

Data and interfaces · 13

Data model

Three SQLite tables with no foreign keys. Layout and scene are stored as JSON documents, so the schema does not know about placements or content types. CREATE TABLE IF NOT EXISTS on every connection is the only migration.

Wall state (memory, state.wall)

{
  "layout": {
    "width": 2000, "height": 1000,
    "placements": {
      "<uuid4>": { "device_id": "<uuid4>",
        "x": 0, "y": 0, "w": 1000, "h": 1000,
        "bezel": {"top":0,"right":0,"bottom":0,"left":0} } } },
  "scene": { "content": { "type": "image",
      "asset": "sha256:…", "fit": "cover",
      "intrinsicWidth": 3840, "intrinsicHeight": 2160 },
    "layout": "active" },
  "revision": 7,
  "generation": "5c1f9a2e"
}

Per-device wall frame (wire)

{ "type": "wall", "revision": 7, "generation": "5c1f9a2e",
  "wall": { "width": 2000, "height": 1000 },
  "scene": { "content": { "type": "image",
      "asset": "sha256:…", "url": "/assets/sha256:…",
      "fit": "cover", "intrinsicWidth": 3840,
      "intrinsicHeight": 2160 },
    "layout": "active" },
  "placement": { "x": 0, "y": 0, "w": 1000, "h": 1000,

Differences from storage: layout is flattened, only this device’s placement is included (without device_id), and url is composed on the way out. A device without the image cap gets {"type":"color"} instead.

Close codes

CodeMeaning
4426Unsupported protocol. Checked before identity.
4400device_id missing or not a UUID4.

Quality and risk · 17

Security boundaries

The app has no authentication. Its security story is a deployment shape: a reverse proxy with two origins, a loopback-only backend, and a browser Origin fence as a second line. This is an architectural map, not an audit.

AreaHow the code handles itWhat to keep in mind
AuthenticationNone in the app. Proxy Basic auth on the operator origin.Never describe the Origin guard as authentication. The code comments say so explicitly.
CSRF / cross-site WSoperator_origin_guard middleware: POST/PUT/PATCH/DELETE need exactly one matching Origin. /ws/controller is denied with HTTP 403 before accept. Registration is the one exempt write.Non-browser clients can forge Origin. An invalid configured value fails closed.
Device identityUUID4 chosen by the tablet itself.An identifier, not a credential. Pairing and revocation are open decisions.
Untrusted filesTop-level regular files only, O_NOFOLLOW, fstat re-check, 10 MiB / 12 MP caps, full decode, re-hash on serve, nosniff.Pillow parses untrusted bytes; keep it updated. Assets are readable by any tablet-origin client.
SQLAll values are bound parameters; interpolated table names come from a module constant.Keep names out of f-strings.
XSS in the controllerSnapshot names and ids are written as text nodes or encoded path components.Keep using textContent, not innerHTML, for server data.
SecretsNo secrets in the app. Caddy reads a password hash from WALL_OPERATOR_PASSWORD_HASH.Never commit a plaintext password.

How isolation works

tests/conftest.py has an autouse fixture. It points TABLET_WALL_DB and TABLET_WALL_ASSET_DIR at a per-test temp path, unsets the origin variables, and clears the shared dicts through main. TestClient(main.app) runs the real lifespan, so startup code is exercised every test.

Mocked: save_state (monkeypatched to fail), timing constants (patched on main.hub), the browser DOM and canvas (JS test). Not mocked: SQLite, the filesystem, Pillow.

Confidence, honestly

  • High for the server contract: what is stored and what frames are sent.
  • Medium for the tablet renderer: math and races, with fake APIs.
  • Low for controller.js: no automated tests found for its 4,088 lines.
  • None for real pixels, Safari/Chrome quirks, TLS, Caddy, hotspot radio, sleep/kiosk. See deploy/KIOSK.md gates.

How to change the system safely

Realistic changes, with the files in the order you should touch them, the interfaces that can break, the tests to add, and the invariants to keep.

Invariants for every change. Persist before apply before broadcast. No await inside a mutation. Mutate shared objects in place. Full-state frames, never deltas. Never send content a device did not advertise. Keep layout and scene separate. Update PROTOCOL.md with any wire change. Run one worker.
