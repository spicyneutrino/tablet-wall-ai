01

What this project is

purpose · users · vocabulary

tablet-wall-ai turns a set of tablets into one coordinated display wall. A Python server serves two browser pages. Each tablet opens the client page, registers itself, holds a live socket, and paints its slice of a shared logical canvas. The operator opens the controller page to watch the roster, arrange tablets on the wall, choose what is shown, and save or recall arrangements.

🖥 Tablet client

One browser page per tablet. Identity in localStorage, re-registers before every socket attempt, renders colour, calibration, or its slice of a curated image.

frontend/client/client.js

🎛 Operator controller

Dashboard with device tiles, a numeric placement editor, a wall map, content controls, an asset browser, and named layout/scene save & recall.

frontend/controller/controller.js

🧠 Wall state

A layout (dimensions + placements) and a scene (content), plus a revision and a generation token that make reconnect and restore safe.

tabletwall/state.py · persist.py

🖼 Curated images

Operator copies JPEG/PNG files into a directory. Assets are addressed by the SHA-256 of their bytes; there is no upload endpoint.

tabletwall/assets.py

Three things the wall can show

Content typeWhat each tablet rendersIntroduced

Vocabulary the code assumes

Wall — one logical canvas in abstract integer units, not pixels or millimetres. Default 2000×1000.

Placement — rectangle {x,y,w,h} plus a per-edge bezel inset. The visible rect is footprint minus bezel.

Layout — wall size + placements map. Scene — content + a reference to the active layout.

Reservation — a placement whose device is absent from the roster; it is kept, not pruned, so a returning tablet reclaims its slot.

Revision — a monotonic counter, persisted. Generation — re-minted on every server start.

A client accepts a frame if the generation changed, or the revision is newer.

Asset — a curated image addressed as sha256:<64 hex>. A rename preserves identity; replacing bytes mints a new asset.

Where state lives — in one breath. Roster, sockets, presence, and last_seen are process memory. The active wall, revision, and named snapshots are SQLite. Image bytes are files; the database holds only references. Device identity is the browser's localStorage. Nothing is stored in the browser on the controller side.

Explicit absences (do not assume these exist)

  • No authentication or authorization. The optional operator-Origin check is a CSRF fence, not auth.
  • No AI, no model, no planned schema space for one. The name is historical.
  • No video, no upload endpoint, no clock synchronisation (Phase 4 is a conditional prototype).
  • No container files, no CI workflow, no external service dependency.
  • No drag-and-drop wall editor: placements are numeric inputs, saved explicitly.

Commands over HTTP, events over WebSocket

Every command is an HTTP request with a real status code and response body. WebSockets carry liveness and server→client push. The controller only listens on its socket; it never sends meaningful frames up it.

PROTOCOL.md · "Transports"

One process, by design

Active wall state, sockets, and broadcasts are process-local. Two workers against the same SQLite file would diverge and could overwrite revisions, so the system runs one worker per wall.

Dependency direction

The module graph is acyclic and points one way. main.py knows everything; hub knows state + protocol; state knows protocol; persist and assets are leaves. protocol.py imports nothing from the package, so both state and hub can depend on it safely.

main.py
 ├─> tabletwall/hub.py ──> tabletwall/state.py ──> tabletwall/protocol.py
 ├─> tabletwall/assets.py ─────────────────────────> tabletwall/protocol.py
 ├─> tabletwall/persist.py        (stdlib sqlite3 only)
 └─> tabletwall/protocol.py
Unusual coupling to respect. main.py imports the state objects by name (devices, wall, device_sockets…) and re-exports them. Tests mutate them through main, so they must be mutated in place and never copied or replaced. Reset helpers (main.wall.clear() + update(...)) exist precisely because identity matters.

05

Key design decisions

evidence first · tradeoff included

Each decision below is traceable to code comments, docstrings, or PROTOCOL.md. Expand a card for the evidence, the problem it solves, the tradeoff, alternatives, and the consequence of changing it.

D1Commands over HTTP, events over WebSockettwo protocols, one direction each
Decision

State-changing operations are HTTP requests with real responses; WebSockets carry liveness and server→client push only.

Evidence

PROTOCOL.md · Transportsmain.py · route tablehub.py · _broadcast

Problem solved

A command needs an outcome (delivered, 404, 422, 409) and must survive a socket reconnect. A push needs low latency to many clients.

Tradeoff

Two protocols to keep in sync; a controller must tolerate its own HTTP response and the broadcast arriving in either order. delivered is a best-effort handoff, not a receipt.

Alternatives

Commands over the socket with request IDs; REST + polling (explicitly removed in Phase 1).

If changed

Moving commands onto sockets needs correlation IDs + acknowledgements. Reverting to polling would undo a documented Phase 1 goal.

D2Roster in memory, wall in SQLitevolatile presence, durable arrangement
Decision

Devices, sockets, presence, and last_seen are process state. The active wall, revision, and named snapshots are persisted.

Evidence

tabletwall/state.pytabletwall/persist.pytests/test_persistence.py

Problem solved

Persist what the operator curated; let tablets re-introduce themselves in seconds after a restart.

Tradeoff

Empty roster after restart; placements appear as vacant reservations until tablets return. Presence is never durable.

Alternatives

Persist the roster (needs aging/cleanup policy); memory-only wall (loses operator work).

If changed

Persisting the roster changes delete semantics and needs stale-row cleanup; the client already re-registers on every attempt, so today it self-heals.

D3Layout and scene are separate; recall is one-sidedrecalling content never discards placement work
Decision

layout (size + placements) and scene.content are separate objects with separate namespaces and separate recalls.

Evidence

PROTOCOL.md · Wall statemain.py · PUT /wall /scenetests/test_snapshots.py

Problem solved

Scene recall must not throw away placement work done after the save; layout save must not carry content.

Tradeoff

No single action restores arrangement + content together (a combined preset is explicitly out of scope).

Alternatives

One fused state object; a combined "preset" action.

If changed

Fusing them makes "recall scene" ambiguous — the exact ambiguity the comment warns against.

D4Revision + generation: accept newer, resync on a new lineagethe generation is re-minted on every start
Decision

revision is monotonic within a generation. The generation is fresh on every server start; the revision persists and keeps climbing.

Evidence

main.py:107 _restore_wall_statestate.py:28 _new_generationclient.js:1524 applyWallFrame

Problem solved

A restored or rolled-back DB can hold a lower revision than a connected tablet. Without a lineage token the client would reject the server forever.

Tradeoff

Every restart forces every client to accept and re-render, even if nothing visible changed.

Alternatives

Persist the generation and attempt to detect restores — documented as unreliable from inside the DB alone.

If changed

Do not "optimise" by persisting the generation without solving restore detection; that is the exact failure this avoids.

D5Commit before apply, notify lastpersist → mutate memory → broadcast
Decision

Every wall mutation runs on a detached copy, bumps the revision, and writes SQLite first. Only after the commit does the same change hit live memory and the sockets.

Evidence

main.py:312 _commit_walltests/test_commit_boundary.py

Problem solved

A controller is never told about state that would not survive a restart; no request observes a half-updated wall.

Tradeoff

Each mutation deep-copies the wall and does a synchronous SQLite write in the request path. Cheap at this scale; not for huge walls.

Alternatives

Apply-then-persist with rollback; write-behind queue.

If changed

Any reordering must preserve the invariant — enabling tests exist. Async writes would need a durable outbox.

D6Content-addressed assets, no upload, scan on readthe ID is the hash of the bytes
Decision

Curated files live in a server-local directory; their ID is sha256: + SHA-256 of the bytes. Every read path re-scans and re-validates; serving re-hashes what it read.

Evidence

tabletwall/assets.pyPROTOCOL.md · Still imagestests/test_assets.py

Problem solved

No path traversal, no upload surface, no stale copy: rename preserves identity; replacing bytes mints a new asset; old IDs can never serve new bytes.

Tradeoff

CPU/I-O on every inventory read, acceptance, and serve; operators must copy files and refresh. Keep the directory modest.

Alternatives

Uploads; path-keyed assets; cached inventory — each trades away an invariant.

If changed

An upload endpoint needs its own validation/storage/security design; a cache must preserve "changed bytes ⇒ 404".

D7Protocol majors 1 & 2 with per-device capability downgradea mounted tablet never gets a frame it cannot render
Decision

Sockets negotiate a major (protocol query param; absent = 1). Devices advertise caps; the server rewrites content a device cannot render (image → color).

Evidence

protocol.py:89 _parse_protocolstate.py:166 _wall_framePROTOCOL.md · Protocol versions

Problem solved

Wall-mounted tablets with cached old JS keep working while the contract evolves; v1 sockets never see v2 frames.

Tradeoff

Two frame shapes live in the code; every capability needs a downgrade story.

Alternatives

Simultaneous deploy (impossible for mounted tablets); per-message feature flags.

If changed

A v3 major follows the pattern; never break "absent means v1" without a migration plan.

D8One worker per wall / databaseprocess-local state is a constraint, not an accident
Decision

Run exactly one server process per wall. Sockets, broadcasts, and revisions are process-local.

Evidence

README.md · Known limitationsdeploy/tablet-wall.service.exampletests/test_deployment_guards.py

Problem solved

Avoids cross-process coordination that SQLite cannot provide; two workers against one file would diverge and overwrite revisions.

Tradeoff

No horizontal scaling, no zero-downtime replica swap.

Alternatives

Broker + pub/sub (Redis/NATS) or DB-as-bus — unnecessary at 15–20 tablets.

If changed

Multi-worker requires moving the live wall, sockets, and broadcast into a shared coordination layer first.

D9Operator-Origin guard is defence in depth — never authenticationa browser CSRF fence with no identity
Decision

When TABLET_WALL_OPERATOR_ORIGIN is set, state-changing requests and the /ws/controller handshake must carry exactly one matching Origin. Registration is exempt (tablet origin cannot present it).

Evidence

main.py:434–645tests/test_security.py

Problem solved

Blocks cross-site form POSTs and hostile controller WebSocket handshakes from browsers. Invalid configuration fails closed (403/500).

Tradeoff

Trivially forged by non-browser clients; adds no identity. The real gate is the authenticated proxy in deploy/.

Alternatives

Real authentication — still not implemented; device pairing/revocation belong to later security work.

If changed

Never describe this as auth. Any change must keep the fail-closed behaviour for malformed configuration.

D10Abstract wall units, not millimetresaspect is compared against what the tablet reports
Decision

Wall coordinates are arbitrary integers. Each tablet reports its viewport; the controller warns when a placement's visible rect has a different aspect ratio.

Evidence

PROTOCOL.md · Wall coordinate spaceclient.js · resize re-registercontroller.js · isAspectMismatch

Problem solved

Browser-reported physical metrics (DPR, chrome, zoom) are unreliable; abstract units keep layouts portable and cheap to edit.

Tradeoff

A well-aligned wall needs a calibration pass; pixel-perfect seams are not achievable from a browser without kiosk control. Mismatch degrades to cropping, not distortion.

Alternatives

Declare physical sizes; kiosk APIs (documented as future work in KIOSK.md).

If changed

Physical units would re-introduce the unreliability this avoids; keep the calibration path.

D11Two separate snapshot namespacessaving never touches the active wall
Decision

Saved layouts and saved scenes have separate tables, namespaces, and routes. Saving or deleting a snapshot never bumps the revision or broadcasts.

Evidence

persist.py · saved_layouts / saved_scenestests/test_snapshots.pyPROTOCOL.md · Named snapshots

Problem solved

Recalling one kind cannot smuggle the other in; snapshot inventory is independent of live wall state.

Tradeoff

No combined restore; two recall actions for "the whole look".

Alternatives

A combined preset — explicitly not part of this protocol.

If changed

Keep save/recall asymmetry: recall commits through the boundary; save must stay revision-neutral.

Check yourself

answer first, then reveal

These map to the material above. Try to answer before opening a reveal — the point is retrieval, not recognition.

Q1. A tablet is placed on the wall and goes offline. A new tablet with a different device ID registers. Is the old tablet's placement discarded? What is it called, and what happens when the old tablet returns?

Reveal answer

No. It stays in the persisted placements map. The controller labels it a vacant reservation and offers an explicit Release action. When the old tablet re-registers and reconnects, it reclaims the slot automatically, because the placement is keyed by its persistent device ID.

Q2. A controller sends PUT /scene that sets an image scene. The server writes SQLite successfully. Then the client tablet receives a wall frame with a lower revision than it holds. Under what condition does it accept the frame — and why is that necessary?

Reveal answer

It accepts when the generation differs from the one it holds (then it resets its held revision). The generation is re-minted on every server start, so a restored or rolled-back database — which can come back at a lower revision — still resynchronises instead of being rejected forever. Same generation + revision not newer ⇒ ignore.

Q3. Why does _commit_wall apply the change to a detached copy and write the database first, instead of updating memory and persisting afterwards?

Reveal answer

So a failed write cannot leave memory ahead of disk, and no controller is ever told about state that would not survive a restart. If save_state raises, nothing in memory has changed, the route fails loudly, and no broadcast follows. test_commit_boundary.py enforces this.

Q4. An operator replaces a curated image file with different bytes but keeps the same filename. What happens to existing scenes that referenced the old file?

Reveal answer

Nothing is rewritten. The asset ID is the SHA-256 of the bytes, so the new bytes are a different asset with a different ID. Scenes still reference the old ID; GET /assets/{old-id} re-reads and re-hashes, finds a mismatch, and returns 404, so the tablet shows IMAGE FAILED rather than stale or wrong pixels. The operator must select the new asset (or restore the original bytes).

Q5. Two workers are started against the same SQLite file to handle more tablets. What breaks, and which mechanism specifically would misbehave?

Reveal answer

Each worker has its own in-memory roster, sockets, and live wall. Revisions and recalls could be overwritten, broadcasts would reach only the clients connected to that worker, and presence would disagree between workers. The design is explicitly one worker per wall/database; scaling requires shared coordination first (and the service template intentionally has no --workers).
