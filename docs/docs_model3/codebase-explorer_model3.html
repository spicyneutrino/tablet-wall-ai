1. What this project is

Tablets become one big display. Each tablet shows its own slice of a shared wall. An operator controls it from a browser.

Tablet (client)
Opens /client/. Registers itself. Holds a WebSocket. Paints its slice on a canvas.
Operator (controller)
Opens /controller/. Sees the roster. Places tablets. Chooses colour, calibration, or an image.
Server
One Python (FastAPI) process. Holds state in memory. Saves the wall to SQLite.
Simple mental model. One process holds the state. Everyone keeps a WebSocket open to it. Operators change state with HTTP. The server saves to SQLite first, then pushes the new state to everyone.

4. Main flow: operator shows an image

Trigger: the operator picks an asset and presses “Show on wall”. Press Next to step through.

Why do the seams line up?
Every tablet computes the same image rectangle in wall coordinates: s = max(W/iw, H/ih), centred. Then it maps its own visible rect (placement minus bezel) onto its screen. Neighbours agree on where the picture is.

6. State: device lifecycle

From PROTOCOL.md and hub.py. “Online” means: open socket and a heartbeat within 15 s.

FACT A device must register before its socket is accepted (4404 otherwise). A newer socket for the same id replaces the old one (4409).

Wall state: revision and generation

revision goes up by 1 for each accepted layout or scene change. Tablets ignore a frame whose revision is not newer — but only if the generation is the same.

generation is a new random token on every server start. After a restore or rollback, revision may go backwards. A new generation tells tablets: “accept this and reset what you hold.”

client.js applyWallFrame → if (heldRevision !== null && generation === heldGeneration && revision <= heldRevision) drop;

7. The commit boundary

The most important rule in the server. Every route that changes the wall goes through main._commit_wall.

1. Copy
proposed = deepcopy(wall)
2. Mutate copy
change(proposed); revision += 1
3. Save
save_state(proposed) — if this raises, stop. Memory untouched.
4. Apply live
change(wall); revision += 1
5. Broadcast
Route calls await _broadcast_wall() afterwards.

FACT No await runs inside steps 1–4, so no other coroutine sees a half-changed wall. Tested in tests/test_commit_boundary.py.

INFERENCE The sqlite write is synchronous on the event loop. Fine for tiny writes. A slow disk would delay heartbeats.

Stage 1 — Understand first

  3. tabletwall/protocol.py, then state.py

Stage 3 — Advanced
  1. assets.py and the client image-load logic
  2. controller.js
  3. Origin guard in main.py, deploy/, simulator/

Why this order: the contract and the state come first. Every other file produces or consumes them.
